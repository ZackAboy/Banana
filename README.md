# Banana Lens

**Take a photo. Know what it is. Know what it’s worth.**

A Banana Hacks visual shopping assistant that turns a product photo into an
identity, matching offers, review evidence, and a concise purchasing perspective.
When the exact product is unclear, it requests another useful photo instead of
pretending to know. The default is a complete **synthetic demo**. Live local OCR + Search + Fusion identification is implemented, with optional
Gemini fallback; other live integrations remain unfinished. See the
[runtime setup and DualSense manual test](src/lib/identification/RUNTIME.md).
Live failures never silently fall back to fake data.

## Start locally

Use **Node 24 LTS** (`.nvmrc`; compatible Node 22.22.2+ is also supported).

```sh
nvm use
npm ci
test -e .env.local || cp .env.example .env.local
npm run dev
```

Open <http://localhost:3000>. No credentials or paid services are needed in demo
mode. If your system npm fails during peer resolution, use a current npm release
with the supported Node version. Dependencies are pinned in `package.json` and
`package-lock.json`.

`next-env.d.ts` is generated by the installed Next.js version and is ignored by
Git; keep the local file and its `tsconfig.json` include entry. On a fresh checkout,
run `npm run dev`, `npm run build`, or `npx next typegen` before the standalone
TypeScript check. See [Next.js TypeScript guidance](https://nextjs.org/docs/app/api-reference/config/typescript#next-envdts).

## Try the demo

1. Choose **Instant match** in the Demo selector, then upload/drag in a JPEG,
   PNG or WebP, or use the shutter/gallery control. Picking a photo starts scanning.
2. See the sample LG monitor and illustrative prices, reviews and verdict.
3. Start a new scan and choose **Needs a label** before picking a photo. The
   result requests a label; **Add photo** preserves existing views. Add another
   photo to rescan all views, or explicitly select the synthetic candidate.
4. Toggle light/dark appearance; the initial theme follows your system.

The demo ignores image content and always uses the documented sample product.
All evidence, prices, retailers, and opinions are synthetic fixtures. Offer/review
links point to `example.com` placeholders; the candidate link goes to the sample
manufacturer page. No actual Reddit opinions or current prices have been fetched.
The app announces demo mode and labels synthetic results throughout the UI.

Uploads allow 4 images, 3 MB per file, and 4 MB total. The aggregate limit leaves
room under Vercel's function payload limit. Browser previews use transient object
URLs; the server processes files in memory and never permanently stores them.
It checks MIME, size, count, aggregate size, and file signatures. Full image
normalization/decoding remains future coordinated image-validation work; Gemini rejects files
that pass signature checks but cannot actually be decoded.

## Stack and structure

Next.js 16 App Router, React 19, strict TypeScript, Tailwind CSS 4, locally owned
shadcn/ui Button/Card/Badge primitives, Radix Slot, Lucide React, Zod,
official `@google/genai` SDK, Vitest, ESLint, Prettier, npm, and Playwright.
`components.json` is ready for additional shadcn/ui components. No auth, database,
Redis, Docker, or background workers. A separate optional Python health-only
service is scaffolded; the Next.js app runs independently of it.

```text
src/
  app/                  Pages, layout, styles and thin API route handlers
  components/           Upload, identification, prices, reviews, recommendation, UI
  schemas/              Runtime domain and API validation; source of shared types
  types/                TypeScript types inferred from schemas
  lib/
    ai/                 Gemini client, identification and review-analysis adapters
    search/             Lens, Shopping and review-search adapters
    products/           Verification, normalization and offer sorting
    providers/          Shared interfaces and explicit mock/live selection
    identification/     Source-independent evidence adjudication boundary
    services/           Application coordination and cached price/review workflows
    mock/               Dedicated synthetic fixtures and provider implementations
    cache/              Bounded in-memory TTL cache and in-flight deduplication
    config/             Server environment/model configuration
    api/                Client validation, bounded requests, server error handling
    upload.ts           Shared upload limits and validation helpers
tests/                  Schema, utility, cache and API tests; browser demo tests
vision-service/         Independent FastAPI health scaffold; no inference/models
```

See [ARCHITECTURE.md](ARCHITECTURE.md) for complete data flow, evidence reasoning,
verification, multi-image support, caching, and service boundaries. See
[AGENTS.md](AGENTS.md) and [CONTRIBUTING.md](CONTRIBUTING.md) before team changes.
[HANDOFF.md](HANDOFF.md) records validation, shared contracts, exact files, and

## API contracts

Successful responses include `meta: { mode: "mock" | "live", notice: string | null }`.
Errors use `{ error: { code: string, message: string } }`. All responses are
`Cache-Control: no-store`; application services own caching.

| Route                       | Request                                                                            | Response                   |
| --------------------------- | ---------------------------------------------------------------------------------- | -------------------------- |
| `POST /api/identify`        | Multipart repeated `images` files, optional `scenario` (`confirmed` / `follow-up`) | `{ identification, meta }` |
| `POST /api/products/verify` | JSON `{ candidateId, identification }`                                             | `{ identification, meta }` |
| `GET /api/prices`           | `brand`, `productName`, `modelNumber`, `variant` query                             | `{ offers, meta }`         |
| `GET /api/reviews`          | Same product query                                                                 | `{ insights, meta }`       |

The frontend only fetches prices/reviews after confirmation and requires an exact
model number. It runs the requests concurrently with independent errors/retries.
The APIs are stateless: product queries are not proof of prior identification;
live adapters must verify result relevance themselves. `/api/analyze` is optional
and omitted to keep the starter simple.

## Environment

| Variable              | Purpose                                                      |
| --------------------- | ------------------------------------------------------------ |
| `USE_MOCK_SERVICES`   | `true` (default): explicit demo; `false`: live adapters      |
| `IDENTIFICATION_MODE` | `evidence` (default) or explicit legacy `gemini`             |
| `OCR_PYTHON`          | Absolute executable in the provisioned local OCR environment |
| `OCR_TIMEOUT_MS`      | Local process timeout: default 60000; range 1000–180000 ms   |
| `GEMINI_API_KEY`      | Server-only Gemini credential                                |
| `GEMINI_VISION_MODEL` | Centralized multimodal model selection                       |
| `GEMINI_TEXT_MODEL`   | Centralized summarization model selection                    |
| `SERPAPI_API_KEY`     | Server-only Lens, Shopping, Search credential                |

`.env.example` contains illustrative `gemini-2.5-flash` model settings; validate
availability against the [Gemini model catalog](https://ai.google.dev/gemini-api/docs/models).
Names are configurable and not hardcoded in adapters. Never use `NEXT_PUBLIC_`
for API keys. `.env.local`, other environment files, and deployment state are
ignored; only `.env.example` is intended for version control.

Live evidence mode needs the provisioned local OCR environment and a SerpApi
key for independent external evidence. Gemini is optional when both key and vision
model are configured. Missing OCR can use semantic family fallback, but cannot
confirm in evidence mode. Component failures never become demo evidence. See the
[runtime guide](src/lib/identification/RUNTIME.md) for exact limits and errors.
Unfinished adapters still return `501 PROVIDER_NOT_IMPLEMENTED`.

## Perform one real Gemini identification locally

1. Use Node 24 (`nvm use`) and install dependencies (`npm ci`) if needed.
2. Copy `.env.example` to `.env.local` **only if `.env.local` does not already
   exist**. Edit these server-only settings in `.env.local`:

   ```dotenv
   USE_MOCK_SERVICES=false
   IDENTIFICATION_MODE=gemini
   GEMINI_API_KEY=your-real-key
   GEMINI_VISION_MODEL=gemini-2.5-flash
   ```

   Use a multimodal model supporting JSON structured output that is available
   to your key. The model above is an example, not an adapter default. No
   `SERPAPI_API_KEY` or `GEMINI_TEXT_MODEL` is needed. Never commit `.env.local`.

3. Start (or restart after editing configuration) with `npm run dev`.
4. In another terminal, send **one** request with an actual local product photo
   and a clear label photo of the same product (replace both paths):

   ```sh
   curl --fail-with-body --silent --show-error \
     -F 'images=@/absolute/path/product-front.jpg;type=image/jpeg' \
     -F 'images=@/absolute/path/product-label.jpg;type=image/jpeg' \
     http://localhost:3000/api/identify
   ```

   For a single-photo test omit the second `-F` line. Use JPEG, PNG, or WebP
   with its matching MIME type, at most four files, 3 MB each and 4 MB total.
   Both images are analyzed together in one Gemini call, with automatic retries
   disabled and a 60-second timeout. This manual call consumes real Gemini quota.

5. Inspect `{ identification, meta }`: `meta.mode` must be `live`, with a null
   notice. Inspect faithful `visibleText`, observed `distinguishingFeatures`,
   `reasoning`, status, and `suggestedNextImage`. A readable exact model label can
   support confirmation; ambiguous images should remain likely/uncertain.
   `candidates` is empty in this milestone. Error responses retain the existing
   `{ error: { code, message } }` envelope and never contain mock results.

The provider uses the installed official Google Gen AI SDK's `generateContent`,
inline image data, and [JSON structured output](https://ai.google.dev/gemini-api/docs/structured-output).
The private response schema is derived from the existing Zod identification
schema plus image-indexed evidence. Zod validates the response before an evidence
policy can downgrade unsupported confirmation or conflicting views; it never
upgrades a cautious result using numeric confidence. Likely/uncertain results
always include a useful next photo request. Perception and semantic uniqueness
of visual clues still depend on Gemini and are not independent verification.

Use the endpoint directly for this milestone: the existing UI may automatically
request prices/reviews after confirmation, and those live adapters still return 501. No UI changes are required for the identification contract. Automated tests
mock SDK/model calls, require no key, and consume no Gemini quota. Return to the
demo by setting `USE_MOCK_SERVICES=true` and restarting the server.

## Remaining live work

- **`feature/vision-ocr`:** Python OCR/PaddleOCR, text/identifier extraction and
  normalization, and OCR tests. No Gemini, retrieval, search or UI redesign.
- **`feature/visual-retrieval`:** SigLIP/CLIP, product/candidate embeddings,
  similarity and ranking, and retrieval tests. No OCR, Gemini, search or UI redesign.
- **`feature/product-search`:** external candidates, search/Lens, candidate
  normalization and verification, then shopping. Lens is one source rather than
  the sole identification mechanism.

OCR + Search + deterministic Fusion now run behind the existing frontend contract.
Runtime retrieval, richer association and shopping/review implementations remain
separate work. YOLO remains deferred. See the [runtime guide](src/lib/identification/RUNTIME.md)
for evidence limits and manual validation.

The optional [vision service](vision-service/README.md) keeps only its HTTP health
endpoint; OCR is invoked through its existing CLI, not HTTP. Local Python models
and the source checkout must be provisioned separately from Next.js. This path is
not packaged for Vercel/serverless deployment.


Browser tests cover the confirmed demo, additional-image flow, candidate choice,
mobile layout, appearance toggle, invalid input/removal, and independent review
failure/retry. They do not validate actual camera hardware or external providers.
Playwright screenshots/traces stay in ignored `test-results/`.

Known tooling limitation: ESLint 9 is pinned because the current React/import/
accessibility plugins in Next's configuration do not declare ESLint 10 support.
The initial `npm audit` reported a high-severity `braces` advisory through Next's
**development-only lint dependency chain**; patch availability must be rechecked before a tooling upgrade. Do not force-downgrade Next to npm's suggested
old major. Recheck before upgrading tooling. No application runtime audit
findings were present in the initial verification; rerun `npm audit --omit=dev`
for the current dependency state.

## Vercel

Import the repository in Vercel using the Next.js preset, select Node 24 (or
supported Node 22), and set `USE_MOCK_SERVICES=true` for the demo. Use the default
install command (`npm ci`) and `npm run build`. No credentials are needed for the
mock deployment. There is no permanent image storage and no database migration.
This setup is deployable but has not been published to a Vercel account.
